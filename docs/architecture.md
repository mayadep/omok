# 오목 게임 아키텍처 및 기술스택 검토

작성일: 2026-10-14 · 상태: **검토 요청 (코드 작성 전)** · 저장소: https://github.com/mayadep/omok

## 1. 요구사항 정리

| 구분 | 내용 |
|---|---|
| 핵심 | 사람 대 사람 실시간 대전 |
| 매칭 실패 시 | 일정 시간(기본 5초) 안에 상대가 없으면 AI(자체 알고리즘)와 대전 |
| 성장 | 급수(18급 ~ 1급, 1단 ~ 9단) 구분, 랭킹 시스템 |
| 디자인 | 화면이 단순한 만큼 최대한 고퀄리티 (질감, 조명, 애니메이션, 사운드) |
| 화면 구성 | 정사각형 오목판 중앙, 위쪽에 상대 (캐릭터·레벨·아이디), 아래쪽에 플레이어 (캐릭터·레벨·아이디) |

## 2. 플랫폼 기본값: 모바일 우선 웹 (PWA)

플랫폼이 정해지지 않아 **세로형 모바일 화면을 기준으로 한 반응형 웹앱(PWA)** 을 기본으로 잡았습니다.

- 요청한 레이아웃(위 상대, 가운데 정사각형 판, 아래 나)은 세로 화면에 가장 잘 맞습니다. PC에서는 같은 레이아웃을 가운데 정렬로 보여줍니다.
- 링크 하나로 바로 접속해 대전할 수 있어 초기 사용자 확보와 테스트가 빠릅니다. 앱스토어 심사가 없습니다.
- PWA로 홈 화면 설치가 되고, 나중에 앱스토어 출시가 필요하면 **Capacitor** 로 같은 코드를 iOS/Android 앱으로 감쌀 수 있습니다.
- 처음부터 네이티브 앱(Unity, Flutter)을 고르면 개발 속도가 느려지고 서버·클라이언트 언어가 갈립니다.

## 3. 전체 구조 (Vercel + Neon 기준)

> 2026-10-14 수정: 서버를 **Vercel + Neon** 으로 쓰기로 해서 구조를 바꿨습니다.
> Vercel은 요청이 올 때만 잠깐 실행되는 서버리스 방식이라, 연결을 계속 붙잡고 있어야 하는 실시간 통신(WebSocket)을 직접 할 수 없습니다.
> 그래서 실시간 알림은 **Ably**(실시간 메시지 전달 서비스)에 맡기고, 착수 검증과 승패 판정은 Vercel API가 합니다.

### 각 부품이 하는 일

| 부품 | 비유 | 하는 일 |
|---|---|---|
| **Next.js (Vercel)** | 가게 건물 + 직원 | 화면을 보여주고, API로 "이 수 둬도 돼?"를 검사·판정 |
| **Neon (PostgreSQL)** | 장부 | 유저, 급수 점수, 진행 중인 판, 기보를 저장 |
| **Ably** | 확성기 | "상대가 (7,8)에 뒀다"를 양쪽 화면에 즉시 전달 |

```
┌──────────────────────── 브라우저 (웹 / PWA) ────────────────────────┐
│ React UI + PixiJS 오목판 + 공유 규칙 엔진(금수 미리보기)             │
└──────┬───────────────────────────────────────────▲──────────────────┘
       │ ① 착수 요청 (HTTPS)                        │ ④ 상대 수 실시간 수신
┌──────▼───────────────────────────┐        ┌──────┴──────────────────┐
│ Vercel: Next.js API (서버리스)   │ ③ 발행 │ Ably (실시간 채널)       │
│ - 착수 검증, 금수, 승리 판정     ├───────►│ game:{id}, user:{id}     │
│ - 매칭, 5초 후 AI 배정          │        └─────────────────────────┘
│ - AI 수 계산, 급수 점수 계산     │
└──────┬───────────────────────────┘
       │ ② 저장/조회
┌──────▼───────────────────────────┐
│ Neon (PostgreSQL)                │
│ users, games, moves, ratings,    │
│ match_queue                      │
└──────────────────────────────────┘
```

### 저장소 구성

```
omok/
├─ apps/web/        Next.js (화면 + API), Vercel에 배포
├─ packages/
│  ├─ engine/       오목 규칙·판정 (순수 TS, 화면/API/AI 공용)
│  ├─ ai/           AI 탐색 엔진
│  └─ db/           Drizzle 스키마, Neon 연결
```

규칙 엔진 하나를 화면(금수 위치 표시), API(최종 판정), AI가 같이 씁니다. 판정은 항상 서버(API)가 하고, 화면은 Ably에서 **듣기만** 할 수 있는 토큰을 받기 때문에 가짜 수를 보낼 수 없습니다.

## 4. 핵심 흐름

### 4.1 매칭

1. "대전 시작"을 누르면 API가 `match_queue` 테이블에 넣고, 레이팅이 비슷한 대기자가 있는지 찾습니다 (동시에 두 명이 같은 상대를 잡지 않도록 행 잠금 사용).
2. 있으면 대국을 만들고 두 사람의 `user:{id}` 채널로 "매칭됨"을 보냅니다. 없으면 화면은 대기 연출을 보여주며 기다립니다.
3. 기다리는 동안 몇 초마다 API에 다시 물어보며 검색 범위를 넓힙니다 (±100 → ±200 → ...).
4. **5초가 지나면** API가 아직 매칭되지 않은 것을 확인하고, 플레이어 급수에 맞춘 AI와 대국을 만듭니다.
5. 흑/백은 레이팅이 낮은 쪽이 흑, 같으면 무작위입니다.

### 4.2 대국

- 착수: 화면이 `POST /api/games/{id}/move` 로 보내면 API가 Neon에서 판을 읽어 검증하고, 저장한 뒤 Ably로 양쪽에 알립니다.
- 같은 판에 동시에 요청이 와도 꼬이지 않도록 판마다 버전 번호를 두고 저장할 때 확인합니다.
- 시간 제한: 각 수의 마감 시각을 DB에 저장합니다. 마감이 지나면 상대 화면이 "시간 초과"를 요청하고, API가 서버 시각으로 확인해 판정합니다. (서버리스라 서버가 타이머를 직접 돌리지 않는 방식)
- 연결이 끊겨도 판 상태가 Neon에 있으니 다시 들어오면 그대로 이어집니다. 60초 안에 안 돌아오면 상대가 기권승을 요청할 수 있습니다.

### 4.3 AI

- **알고리즘**: 패턴 평가(열린 4, 4, 열린 3 등) + 위협 탐색 + 알파베타 가지치기, 반복 심화. 후보 수는 놓인 돌 주변 2칸으로 제한해 빠르게 계산합니다.
- **난이도**: 탐색 깊이, 시간 제한, 일부러 차선 수를 두는 확률로 조절해 급수별로 맞춥니다 (18급 AI ~ 고단 AI).
- **실행 위치**: 사람이 수를 두면 같은 API 요청 안에서 AI가 1초 안팎으로 다음 수를 계산해 저장하고 Ably로 보냅니다. 화면에서는 0.5~2초 생각하는 연출을 넣습니다.

### 4.4 급수와 랭킹

- 내부 점수는 **Glicko-2** 레이팅을 씁니다. 판 수가 적은 신규 유저는 점수가 빠르게 움직여서 금방 제 급수를 찾습니다.
- 표시 급수는 레이팅 구간으로 나눕니다. 예: 1000 미만 18급, 100점마다 한 급, 1급 다음 1단 ~ 9단.
- 랭킹은 Neon에서 레이팅 순으로 조회합니다 (인덱스로 충분히 빠름). 시즌 단위(예: 월간)로 스냅샷을 남깁니다.
- 프로필의 "레벨"은 급수/단으로 표시합니다.

## 5. 화면 구성과 디자인 방향

```
┌─────────────────────────┐
│ [캐릭터] 상대ID   3급   │  ← 상대 정보 + 남은 시간
│          ●●○ 대국 타이머 │
├─────────────────────────┤
│                         │
│     15×15 정사각형 판    │  ← 화면 폭에 맞춘 정사각형
│                         │
├─────────────────────────┤
│ [캐릭터] 내ID     5급   │  ← 내 정보 + 남은 시간
│        기권 · 무르기요청 │
└─────────────────────────┘
```

고퀄리티를 위해 이렇게 잡았습니다.

- **오목판**: PixiJS(WebGL)로 그립니다. 비자나무 결 텍스처, 부드러운 조명과 그림자, 돌을 놓을 때 살짝 튀는 애니메이션과 착수음, 마지막 수 표시, 승리 시 다섯 돌을 잇는 빛 효과.
- **UI**: React + Tailwind CSS + Motion(Framer Motion)으로 패널, 전환, 매칭 대기 연출을 만듭니다.
- **캐릭터**: 처음에는 2D 일러스트 아바타 세트(8~12종)로 시작하고, 이후 Rive나 Spine으로 표정·반응 애니메이션을 추가할 수 있습니다. 캐릭터 그림 자산이 필요합니다.
- **디자인 시스템**: 색, 글꼴, 간격을 토큰으로 정리해 다크 톤의 고급스러운 테마를 기본으로 합니다.

## 6. 기술스택 검토

### 6.1 추천 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | **TypeScript** (전 구간) | 규칙 엔진과 타입을 화면·API·AI가 공유 |
| 클라이언트 | **React 19** (Next.js 안에서) | 빠른 개발, 생태계 |
| 오목판 렌더링 | **PixiJS v8** | WebGL 이펙트·애니메이션을 가볍게, 모바일에서도 60fps |
| UI/애니메이션 | **Tailwind CSS + Motion** | 고퀄리티 UI를 빠르게 반복 |
| 상태관리 | **Zustand** | 단순하고 가벼움 |
| 웹 + API | **Next.js (App Router)** on **Vercel** | 화면과 API를 한 프로젝트로, Vercel에 바로 배포 |
| 실시간 통신 | **Ably** | Vercel은 WebSocket을 유지할 수 없어서 실시간 전달을 맡김. 무료 구간이 넉넉하고 재접속·순서 보장 지원 |
| DB | **Neon (PostgreSQL) + Drizzle ORM** | 유저·대국·기보·레이팅·매칭 대기열. Vercel과 연동이 쉬움 |
| 인증 | **Auth.js** 게스트 즉시 시작 + 구글/카카오 로그인 | 진입 장벽 최소화, 나중에 계정 연결 |
| 모노레포 | **pnpm workspaces + Turborepo** | 패키지 공유와 빌드 캐시 |
| 테스트 | **Vitest** (엔진·AI), **Playwright** (E2E) | 규칙 엔진은 테스트로 촘촘히 검증 |
| 배포 | **Vercel** (웹 + API) · **Neon** (DB) · **Ably** (실시간) | 셋 다 무료 구간으로 시작 가능, 사용량에 따라 확장 |

### 6.2 검토한 대안

| 대안 | 판단 |
|---|---|
| **Unity** | 연출은 강하지만 웹 빌드가 무겁고 첫 로딩이 느림. 2D 보드게임에는 과함. 3D 연출이 핵심이 되면 재검토 |
| **Flutter** | 모바일 앱에는 좋지만 웹 성능·SEO가 약하고 서버와 언어가 갈림 |
| **Fastify + Socket.IO 별도 서버** | 처음 안이었음. 실시간 처리는 가장 자연스럽지만 Vercel 밖에 서버를 하나 더 운영해야 해서, Vercel + Neon 방침에 맞춰 Ably로 대체 |
| **Pusher / Supabase Realtime** | Ably와 같은 역할의 대안. Pusher도 무방하고, 무료 한도와 메시지 순서 보장 때문에 Ably를 우선 선택 |
| **Colyseus** | 게임 방·매칭 내장 프레임워크지만 상시 실행 서버가 필요해서 Vercel 방침과 맞지 않음 |
| **Firebase/Supabase Realtime 만 사용** | 서버 판정 권한(치트 방지)과 타이머 처리가 어려움 |
| **SVG/CSS 오목판** | 구현은 쉽지만 조명·파티클 같은 고급 이펙트에 한계. 고퀄리티 요구 때문에 PixiJS 선택 |

## 7. 단계별 개발 계획

1. **엔진**: 오목 규칙·승리 판정·금수 판정 + 테스트
2. **오프라인 프로토타입**: 고퀄리티 오목판 화면 + AI 대전 (서버 없이 플레이 가능)
3. **실시간 대전**: 대국 API + Ably, 매칭, 5초 후 AI 배정, 재접속
4. **계정과 급수**: 게스트/소셜 로그인, Glicko-2, 급수 표시, 랭킹
5. **디자인 다듬기**: 캐릭터 자산, 사운드, 연출, PWA 설치
6. **배포와 운영**: 모니터링, 부정행위 탐지(엔진 사용 의심 등)

## 8. 결정이 필요한 사항

1. **룰**: 렌주룰(흑만 3-3·4-4·장목 금지, 대회 표준) vs 국내 일반 오목룰(양쪽 3-3 금지) vs 자유룰. **추천: 렌주룰** (흑의 선수 이점을 줄여 랭킹전이 공정해짐)
2. **AI 대전 표시**: AI 상대임을 화면에 표시할지. **추천: 표시하고 급수 점수는 절반만 반영** (상대를 속이지 않고, AI로 점수를 쌓는 악용 방지)
3. **플랫폼**: 모바일 우선 웹(PWA)으로 시작해도 되는지. **추천: 웹으로 시작, 앱스토어는 Capacitor로 나중에**
4. **실시간 서비스**: Ably 계정이 필요합니다 (무료). Pusher를 선호하시면 바꿀 수 있습니다.
5. **캐릭터 자산**: 직접 준비한 그림이 있는지, 없으면 우선 임시 아바타로 진행
